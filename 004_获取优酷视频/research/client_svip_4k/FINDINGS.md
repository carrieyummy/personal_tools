## 2026-11-17 第三轮续研：从元数据进入实际媒体

### 清单与分段实测

本轮继续使用客户端已经打开的同一集和 `hls5hd4_hbr_bit10`，没有降档。读取实时 UPS 中的实际 M3U8 地址，收到 HTTP 200、178179 字节的媒体清单：243 段、5 处不连续标记、完整 `EXT-X-ENDLIST`，声明总时长 `2747.033333` 秒。这是当前播放编排的总时长，不直接等于无广告正片时长。

清单没有标准 `EXT-X-KEY`；各段有 `EXT-X-PRIVINF`。本机 SDK 使用 `!segment.info.DRM_NOTENCRYPT` 判断私有保护状态，因此**缺少标准 KEY 标签不能证明未加密**。以下三个正片抽样只有 `FILESIZE`，未设置 `DRM_NOTENCRYPT=1`；三者位于同一连续区间。抽样位置从 YAML 读取，本次为按清单分段序号比例的 5%、50%、95%，不是严格的时间百分比。

| 清单序号（从 0 开始） | 清单段时长（秒） | 实际字节数 | HTTP 长度及 FILESIZE | 普通 FFmpeg 完整抽样解码 |
| --- | --- | --- | --- | --- |
| 12 | 14.40 | 2001448 | 均匹配 | 失败 |
| 121 | 8.64 | 1633344 | 均匹配 | 失败 |
| 230 | 11.76 | 4387732 | 均匹配 | 失败 |

三个文件都具有完整的 188 字节 TS 包边界及同步字节，传输层 `scrambling_control` 都为 0。FFmpeg 能探测 MPEG-TS、HEVC 和 AAC，却不能取得有效视频尺寸和音频采样参数，报 `Invalid data`，退出码为 Windows 无符号值 `3199971767`（有符号值 `-1094995529`），没有超时。这进一步说明 TS 外壳正常不等于音视频负载可直接解码；当前证据不支持直接二进制合并或仅使用 `-c copy` 就能获得可播放文件。

### 媒体处理适配的具体缺口

本机 `9.24.1` SDK 中，TS 自定义保护分支将解复用后的 packet 数据交给 AES-ECB 处理，完整 16 字节块处理后保留不足一块的尾部，再进入编解码器解析。它不是对整个 TS 文件逐 16 字节解密；TS/PES 的结构与有效负载边界需要独立验证。源码证据包含文件哈希、偏移及有限片段，存入本轮归档。

客户端实际使用原生 `key01` 分支。尝试通过当前 SDK 的 Web 挑战函数配合 `web01` 复现桌面请求，服务端返回业务错误 `-4009`；原生会话材料直接送入 Web 处理函数也未验证成功。这些失败不能靠任意修改 UA、换其他账号或降档来报告成功。作为对照阅读的 [Web 实现源码](https://github.com/baipzy123/ttt/blob/main/yk.py) 使用的是另一套请求上下文，不构成本客户端帧享适配的证明，未引入其中的固定签名或密钥。

本轮只读检查原生模块公开方法，发现 `setDrmInfo`、播放、暂停、截图等接口，但未发现直接导出原码流文件的方法；这不证明内部不存在可复用处理能力。未修改安装文件，未向运行中播放器调用未经验证的原生函数，也未把不稳定的地址或猜测的密钥算法写入正式适配代码。

下一步的验收关口是：为当前原生会话建立经过验证的媒体处理适配，使这三个样本先恢复为可完整解码的原始 HEVC/AAC 码流；随后才能做整集分段下载、正片与广告及音轨匹配、无重编码封装，以及全片音视频解码和时长检查。当前不能生成已验证的无损本地成品。转码或录屏会重新编码，不能替代此次无损要求。

### 可复现入口与证据

新增 `media` 采样入口，严格匹配当前样本和配置档位，逐跳校验 CDN 域名，限制清单/分段大小，核对响应长度与私有 FILESIZE；样本按内容摘要命名，保留 SHA-256。仅当前已验证的 TS 媒体清单受支持，主清单、范围分段、初始化段及缺失结构明确失败。媒体请求不装载账号 Cookie 或完整设备 UA。原生 UPS 实际提供 HTTP 媒体 URL，所以允许协议也读 YAML；没有擅自改写签名地址。

新增 `media-verify` 本地验证入口，检查报告来源、样本路径和摘要，强制 MPEG-TS 输入且只允许本地文件协议，明确选择视频及音频流。验证使用 `framehash`，要求真实输出的视频帧与音频帧都大于 0，防止零帧但退出 0 被误判为成功；本轮三个样本的两类帧计数均为 0。FFmpeg 失败或超时会使该命令退出 1；原始 stderr 不写入报告，避免以后混入临时地址。即使抽样全通过，`independent_file_verified` 也保持 false，直到真正完成全片验收。

本轮归档：`reports/media_observed_20261117.json`，包含清单摘要、样本摘要、解码结果、FFmpeg 二进制摘要和 SDK 证据。样本仅保留在 YAML 指定的忽略目录，未保存签名地址、Cookie 或媒体密钥。当前实现不生成 MP4/MKV 成品，也不把失败样本发布为视频。

本轮使用已有 FFmpeg 和 Python 依赖，没有安装新包，`requirements.txt` 无新增条目。`test_runner` 执行 29 项隔离测试及编译检查，均通过；真实 `media-verify` 检查如实退出 1。隔离测试通过证明采样和失败处理按设计工作，不表示媒体解码已经成功。临时 Inspector 在每次采样后回收，播放器仍保持原有暂停状态。

## 2026-11-17 第四轮续研：原生适配与无重编码还原

### 已通过实际音视频解码

当前会话的三个真实分段经还原后，FFmpeg 完整解码均退出 0，没有关键错误或超时：

| 原清单序号 | 视频帧数 | 音频帧数 | 实际视频 | 实际音频 |
| --- | --- | --- | --- | --- |
| 12 | 360 | 620 | HEVC Main 10，3840×2160，25 fps，yuv420p10le | AAC LC，44100 Hz，立体声 |
| 121 | 216 | 372 | 同上 | 同上 |
| 230 | 294 | 507 | 同上 | 同上 |

### 目前验证成功的方法

1. 精确绑定当前播放页的 `vid`、目标帧享类型和原生 `key01` 会话，与已下载样本报告核对尺寸、大小、语言和保护类型；先检查输入文件长度与 SHA-256。
2. 在独立 Electron 子进程读取本次原生挑战。相关材料仅驻内存，经标准输入传给独立 64 位 Python 子进程，调用本机已核验原生库的会话处理函数。
3. 将每个 PID 的 TS 负载重组成完整 PES，识别并保留 PES 头，对音视频有效负载按 SDK 的 AES-ECB packet 分支处理，保留不足 16 字节的尾部，再按原位置写回 TS。TS 头、自适应区、PES 头和时间戳保持原样，输出长度与输入一致。
4. 对还原后的完整分段分别解码视频、音频，要求两类帧数都大于 0 且 FFmpeg 退出 0。之后才进入 `-c copy` 的容器封装检查。

原生库为 `nplayer64/aliplayerVS.dll`，本轮定位函数的 RVA 为 `0x256220`。函数边界、调用点、架构及摘要在 `reports/native_media_adapter_20261117.json` 中。实现复用该已核验函数，不把先前失败的 Web 算法猜测作为运行路径。主进程不直接调用未知 ABI：操作在隔离子进程中，完整 DLL 摘要、挑战模块摘要、64 位架构及函数所在可执行节均须通过校验。配置的摘要与 RVA 共同约束本版本，客户端升级后必须重新分析并完成同等级实测，不能仅更新摘要。

新增 `media-restore` 入口，输入为 `media` 报告，输出候选 TS 和 `media-restore.json`。当前实现针对本轮验证的 TS/PES 帧享流和抽样报告；遇到路径越界、来源变化、摘要不符、连续计数缺口、缺音视频 PES 或不支持的明文段时明确失败。它不自动处理完整整集、不忽略广告/音轨差异，也不把还原命令退出 0 当作解码验收。

本轮独立实验与正式入口使用同一当前播放会话，生成的三个还原文件 SHA-256 一致。正式入口不依赖从历史日志读取授权值。没有修改安装文件、向运行中原生播放器写入代码或改变播放状态；本轮创建的 Inspector 已回收，敏感值未写入配置、命令行或报告。

## 已打通的调用链

1. 从客户端的 `Cookies` 数据库只读加载当前优酷会话，Cookie 值只驻内存。
2. 查询 `mtop.youku.vip.xtop.member.profile.get` 验证权益。
3. 查询 `mtop.youku.pixiu.downloadpanelattr.get` 获取当前样本的实际下载档位，不从前端枚举猜测可下载能力。
4. 使用客户端自身的 Electron，以独立 Node 子进程加载同一安装目录中的 `youku-player.node`，调用 `KAliPlayer.getUpsCKey` 和 `getEncryptR1` 生成请求材料。
5. 按本机缓存播放器代码中的参数构造 `mtop.youku.play.ups.appinfo.get` 请求，记录正片清晰度、尺寸、时长和 DRM 类型。

本次签名运行时是 `Electron 14.2.0 / Node 14.17.0 / ia32`。不要直接用系统 64 位 Node 加载该原生模块。脚本记录模块 SHA-256；客户端升级后应重新核对接口和结果，不能只改路径就宣称适配成功。

两种在线入口均使用 H5 MTop。`online` 继续保留历史静态参数对照；`live` 则读取当前播放页实际构造的参数并重新签名，已成功复现帧享响应。对照组通过 YAML 选择公共域 Cookie 或实际启动日志中的原生 UTDID，以及配置 UA 或日志 UA；日志版本不匹配或缺少所需字段时明确失败，不回退到伪造上下文。

参数对照全部写在 YAML 的 `network.ups.cases`，包含下载参考、桌面播放、帧享选择及续研上下文对照。`user_agent_source` 可选 `template` / `client_log`，`device_source` 可选 `cookie` / `client_log`，`client_hardware_fields` 控制是否附加日志中的硬件字段。主机、版本、能力位和搜索词均读配置，代码没有另设一组运行默认值。

代码也保留播放器源码中的 `enc_ver` 接口元数据处理分支。本次服务器均返回未加密元数据，原生 `getDecryptR1` 分支**未触发，尚未完成真实响应验证**。该分支用于接口元数据，不能当作媒体 DRM 解密实现。

## 距离独立视频文件还差什么

帧享正片流元数据、实际媒体读取及三个分段的原码流还原已验证。剩余工作是整集分段下载与完整性核对、正片/广告和音轨处理、整集容器封装及全片音视频验收。当前原生适配与接口元数据解码是不同流程，服务端声明大小也不能替代完整文件检查。

第四轮已将三个正片分段还原并通过完整音视频解码；会话密钥仅驻内存，没有下载整集，也没有完成全片解码验收。报告中的 `independent_file_verified` 因而保持 `false`。仅有会员 Cookie、4K 标签、M3U8 地址或元数据中的文件大小，都不足以将任务判定为完成。

后续实现必须区分正片、广告、预览以及不同音轨。研究报告给每条流标注 `json_path`；本次正片来自 `$.data.data.stream`，其他广告路径不能参与正片最高画质排名。
